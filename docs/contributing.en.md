# Contributing

CS Retro should grow with its community. Requests and criticism are welcome —
you do not need programming experience.

## Ways to help

- **Playtesting:** precise reproduction steps and understandable screenshots.
- **Ideas:** explain the problem and why a change fits the game's identity.
- **Interface and accessibility:** readability, contrast, scaling and keyboard operation.
- **Documentation and translations:** maintain German and English equally.
- **Code and tests:** focused changes with verifiable results.
- **Attribution:** report missing credits or license information with a reliable source.

[Open an issue](https://github.com/benjarogit/csretro/issues/new/choose){ .md-button .md-button--primary }

## Useful bug reports

Search existing issues first. Include commit/version, operating system, architecture, renderer
and exact steps. Describe expected and actual behavior.
For input bugs, mouse/keyboard buying, selection method and timing matter.

Logs can contain usernames, local paths, IP addresses or passwords.
Sanitize them before uploading. Security issues belong in a
[private vulnerability report](https://github.com/benjarogit/csretro/security/advisories/new),
not a public bug issue.

## Pull requests

1. Fork the repository and create a branch.
2. Discuss larger changes before implementing them.
3. Keep the change focused; avoid unrelated formatting edits.
4. Build and test in proportion to risk; list checks you did not run.
5. Update behavior documentation and both language versions where relevant.
6. Preserve source attribution, authors and license notices.
7. Open a PR explaining the change, linked issue and verification steps.

A green documentation check does not test gameplay. Menu/gameplay changes benefit from
before/after captures and a reproducible test sequence.

## Working together

Be respectful, specific and constructive: no personal attacks, harassment or disclosure of private
information. Discuss ideas in terms of their benefits and effects.
Not every proposal fits; rejections should also explain why.

`good first issue` identifies approachable starting points; `help wanted` requests assistance.
These labels do not guarantee that a task can be completed without questions.
